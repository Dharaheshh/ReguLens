# RULES.md — Engineering Rules and Constraints

These rules are binding. Where a rule here conflicts with a general best practice
you know, this rule wins for this project. Where a rule here conflicts with
another control-plane file, stop and surface the contradiction (see `AGENTS.md`).

## 0. The 18 hard rules (non-negotiable)

1. LLM output is never a source of truth. It is a proposal.
2. A candidate becomes a fact only after deterministic backend validation and a
   successful database write.
3. Every citation ID an LLM proposes must resolve against the `evidence` table
   before it can become a `citations` row.
4. An unresolved/invalid citation ID never becomes a citation — the claim it was
   attached to is downgraded to `UNSUPPORTED`, not silently dropped.
5. No response may reach `status = 'approved'` without an explicit human approval
   action recorded in `audit_events`. There is no automated approval path.
6. Uploaded document text is untrusted data, always.
7. Document text must never be concatenated into a system prompt as if it were
   an instruction. It is always passed as clearly delimited, labeled content.
8. Retrieval finding a chunk does not mean the chunk is true, relevant, or
   sufficient — retrieval only proposes candidates.
9. Semantic similarity between two claims is not evidence of contradiction. Use
   of similarity is limited to deterministic pre-filtering of *candidates*; the
   actual contradiction classification requires the scoped LLM comparison
   defined in `AI_RAG_DESIGN.md`.
10. Sufficiency status is computed from stored `requirement_evidence` coverage
    rows — never asserted directly by an LLM call.
11. Document versions are never overwritten or deleted. A re-upload creates a
    new `document_versions` row; old chunks/evidence/citations remain intact
    and queryable.
12. Every LLM call's response must pass Pydantic schema validation before any
    part of it is used.
13. Every LLM call gets exactly one retry on validation failure, then transitions
    to an explicit failure state (`LLM_FAILED` or `VALIDATION_FAILED`) — never a
    silent fallback to unvalidated output.
14. Exceptions are never swallowed silently. Catch specific exceptions, log with
    context, and surface a defined failure state.
15. No secret, API key, or credential is ever committed to the repository. All
    come from environment variables per `ENVIRONMENT.md`.
16. Tests are never bypassed, skipped, or deleted to make a build pass.
17. No fake/stub implementation is ever left in place pretending to be real
    (e.g., a hardcoded "SUFFICIENT" response instead of calling the real
    sufficiency engine). If something isn't built yet, it must fail loudly, not
    fake success.
18. Do not introduce an "agent" abstraction (autonomous multi-step LLM loop,
    tool-calling agent, etc.) anywhere in this system. Every LLM call in
    ReguLens is a single bounded call with a fixed input/output schema — see
    `AI_RAG_DESIGN.md`. There is no autonomous reasoning loop in this
    architecture, by design.

## Architecture rules

- The pipeline order defined in `ARCHITECTURE.md` is fixed. Do not reorder
  stages, skip a stage, or merge two stages into one implementation without
  an explicit instruction.
- The boundary between RAG (retrieval) and validation (claim/citation/
  contradiction/sufficiency checking) is a hard boundary. Retrieval code must
  never make a truth judgment. Validation code must never perform retrieval.

## Database rules

- All twelve tables in `DATABASE_SCHEMA.md` are the complete approved schema.
  Do not add a table without updating that file first and getting confirmation.
- All schema changes go through a migration (Alembic). No manual DDL against a
  running database, including in local development, once the schema is past
  its initial migration.
- Foreign keys are enforced at the database level, not just checked in
  application code.
- UUIDs are the primary key type for every table, generated by the database
  (`gen_random_uuid()`), never generated client-side.
- Every table that represents a fact created over time gets a `created_at
  TIMESTAMPTZ DEFAULT now()`. Do not omit this to save time.

## API rules

- Every endpoint's request/response shape matches `API_CONTRACT.md` exactly.
  If an endpoint needs a field that isn't in that file, update the file first.
- Use Pydantic models for every request body and response body — no raw dict
  passthroughs.
- Validation errors return HTTP 422 with the standard FastAPI validation error
  format. Business-logic failures (e.g., `INSUFFICIENT_EVIDENCE`) are not
  HTTP errors — they are valid 200 responses with that status encoded in the
  response body, because they are legitimate outcomes, not failures of the API.

## Python rules

- FastAPI + Pydantic v2 throughout.
- Async endpoints where they call the database or an external API (LLM,
  embeddings); synchronous is acceptable for pure computation.
- One module per responsibility, matching the directory layout in
  `ARCHITECTURE.md` (`ingestion/`, `retrieval/`, `generation/`, `validation/`).
- No global mutable state. Configuration comes from a single `Settings` object
  loaded from environment variables.

## TypeScript / React rules

- Strict mode. No implicit `any`.
- API calls go through a single typed API client module — no ad hoc `fetch`
  calls scattered across components.
- Server state (documents, responses, claims) is never duplicated into local
  component state beyond what's needed for in-progress edits; after any
  mutation, re-fetch rather than optimistically mutate local state and hope it
  matches the server.

## PostgreSQL / pgvector rules

- Vector column dimension must match the embedding model in use exactly —
  defined once in `ENVIRONMENT.md` and `AI_RAG_DESIGN.md`, referenced nowhere
  else as a hardcoded number.
- HNSW index is created on the `chunks.embedding` column with cosine distance
  (`vector_cosine_ops`). Do not switch to IVFFlat without an explicit
  instruction — see the architecture contract's reasoning in `ARCHITECTURE.md`.
- Full-text search uses Postgres's built-in `tsvector`/`GIN` index for the
  lexical half of hybrid retrieval. Do not introduce Elasticsearch or any
  external search engine.

## RAG / retrieval rules

- Retrieval always runs both lexical (`tsvector`) and vector (HNSW) search and
  fuses results — never one alone, unless explicitly testing a single channel
  in isolation.
- Reranking (if implemented — see `TASKS.md` for should-have status) operates
  only on the fused candidate set, never on the full corpus.
- Retrieval is always scoped to non-superseded document versions by default.

## LLM / structured output rules

- Every LLM call has a Pydantic response model. The call is made with
  structured-output / schema-enforcing settings where the provider supports it,
  and the response is parsed through that Pydantic model regardless.
- Temperature is set low (≤ 0.3) for every call in this system — drafting,
  extraction, and classification all favor consistency over creativity.
- No LLM call in this system ever sees the full corpus. Every call receives
  only the specific, bounded evidence/claim/context relevant to that call, as
  defined per-call in `AI_RAG_DESIGN.md`.

## Citations, claims, evidence rules

- `Evidence` rows are created once per chunk at ingestion time, not created
  fresh per query.
- A `Citation` row is only created after its `evidence_id` is confirmed to
  exist in the `evidence` table.
- A `Claim`'s `validation_state` is never set directly by an LLM's raw label —
  it passes through the Pydantic schema and the deterministic checks in
  `AI_RAG_DESIGN.md` first.

## Contradiction detection rules

- Candidate historical claims are selected by the deterministic pre-filter
  (same `product_topic`, response status = `approved`) before any LLM call.
- The LLM comparison call never sees the entire historical claim set — only
  the pre-filtered candidates, capped at 10 per new claim.
- A contradiction classification of anything other than `COMPATIBLE` is always
  written to the `contradictions` table and always surfaced to the human
  reviewer. It is never auto-resolved.

## Sufficiency rules

- Sufficiency status is computed by the deterministic aggregation rule in
  `AI_RAG_DESIGN.md` over stored `requirement_evidence` coverage — not by
  asking an LLM "is this sufficient?" directly.
- The coverage score, if shown in the UI, is always labeled as a retrieval-
  coverage measure, never as a scientific-completeness or safety score.

## Document ingestion / versioning rules

- Ingestion preserves page numbers and section headings wherever the parser
  can extract them. A chunk without a resolvable page number is still stored,
  but flagged, not discarded.
- Re-uploading a document creates a new `document_versions` row. The previous
  version's `status` is set to `superseded`, never deleted.
- `documents.current_version_id` always points to the latest non-superseded
  version; retrieval joins against this pointer by default.

## Security rules

See `SECURITY.md` for the full model. The rule that applies to every piece of
code touching document content: treat it as data. Never allow it to be
interpreted as an instruction to any LLM call in the system.

## Logging rules

- Every LLM call logs: which call type, timestamp, success/failure, and (on
  failure) the validation error — never the raw API key or full prompt
  containing sensitive content in plaintext logs beyond what's needed for
  debugging.
- Every state transition on a `responses` row is logged to `audit_events` with
  actor, timestamp, and a structured payload of what changed.

## Error handling rules

- Catch specific exceptions, not bare `except:`.
- On any deterministic-stage failure (retrieval, citation validation, DB
  write), the failure state is explicit and returned to the caller — never
  masked as a partial success.

## Testing rules

- Every task's acceptance criteria include at least one test targeting its
  core behavior. See `TESTING_STRATEGY.md`.
- Tests must actually run and pass before a task is reported complete.

## Git rules

See `GIT_WORKFLOW.md` for branch/commit conventions. The rule specific to this
control plane: a commit that changes a control-plane document (schema, API
contract, architecture) must be a separate commit from any application code
change, and must be called out explicitly in the PR description.
